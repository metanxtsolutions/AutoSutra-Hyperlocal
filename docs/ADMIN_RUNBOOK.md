# Admin runbook

For AutoSutra staff using `/admin`. Every action here is audited with your name; most ask for a reason.

## Staff roles

| Role | Can |
|---|---|
| Super admin | Everything below, plus feature flags, staff roles, plans, user suspension |
| Finance admin | Ledger, payments, refunds, reconciliation, settlements, provider payments, invoices, discounts |
| Campaign operations manager | Managed campaigns (prepare, sign off, publish, pause), connection checks, job retries, support |

Staff cannot approve a customer's budget or raise authorised spend. A super admin cannot change their own staff role or status.

**Two-step verification is required for every staff account.** The admin console opens only in a session that passed the two-step code; new staff are sent to Account → Two-step verification first. If someone loses their phone and recovery codes, another super admin confirms their identity through a separate channel (video call or a known phone number) and uses **Users → Reset two-step**, recording how identity was confirmed.

## Daily

| Check | Where | Action |
|---|---|---|
| Overview counters | `/admin` | Work any non-zero queue below |
| Organisations awaiting verification | `/admin/organisations` | Check GSTIN and business details against documents; verify or reject with a reason. Deposits are blocked until verified. |
| Managed campaigns ready for operations sign-off | `/admin/campaigns` | Review creative, claims and targeting; sign off; publish |
| Failed platforms and failed publication attempts | `/admin/jobs`, campaign page | Read the provider error; fix the cause (reconnect, policy, missing asset) and retry. Never retry a validation error unchanged. |
| Dead or failed jobs | `/admin/jobs` | Read `last_error`; retry once the cause is fixed |
| Connections in error, expired or access pending | `/admin/connections` | Contact the customer to reconnect |
| Reconciliation differences | `/admin/finance/reconciliation` | See finance procedures |
| Refund requests | `/admin/finance/refunds` | See finance procedures |
| Support tickets, contact requests | `/admin/support`, `/admin/contact-requests` | Reply; internal notes are not shown to customers |
| Failed or undelivered emails | `/admin/emails` | Check the SMTP error; a permanent rejection usually means a mistyped address |

## Finance procedures

### Reconciliation (daily, automatic run at night; can be run on demand)

1. Open `/admin/finance/reconciliation` and review open differences: provider spend vs recognised spend, overspend beyond the reservation, deposits without a ledger entry, gateway amount mismatches.
2. For each difference, find the cause (late provider data, a missed webhook, a manual payment).
3. If no money moved incorrectly, **resolve** with a note.
4. If a correction is needed, **propose an adjustment** (amount and direction, reason). A **different** finance user must **approve** it; only then is a compensating ledger entry posted. Nobody edits or deletes ledger rows.

### Refunds (central wallet only)

1. A customer requests a refund of up to their unallocated balance (reserved campaign budgets must be released first). The amount moves to *refund pending* only on approval.
2. A finance user other than the requester checks for unresolved overspend on the organisation, then approves by typing the exact amount, or rejects with a reason (shown to the customer).
3. The refund is paid through the gateway (status from the gateway webhook) or by bank transfer (record the bank reference). A failed refund returns the money to the customer's available balance.

### Settlements and provider payments

- When the gateway settles to the bank, record the settlement (client funds or operating) with the bank reference.
- When AutoSutra pays Meta or Google from client funds, record the provider payment with the invoice reference. This clears media payable.

### Invoices

- Subscription invoices are generated by the nightly billing cycle; service invoices (setup, management fees, add-ons) are issued manually.
- Void an invoice only with a reason; a voided invoice keeps its number. Issue a new invoice for the corrected amount.
- GST: CGST + SGST when the customer's billing state equals the supplier state (supplier state and details are set on `/admin/flags`, which also holds the lead retention period), IGST otherwise.

## Feature flags

`/admin/flags`. Each change needs a reason and typed confirmation and is audited.

| Flag | Turn on only when |
|---|---|
| `live_meta_publishing` | Meta app review approved and a test publication verified (see [PROVIDER_SETUP.md](PROVIDER_SETUP.md)) |
| `live_google_publishing` | Google developer token has Basic access and a test publication verified |
| `central_wallet` | Written legal, gateway, platform and tax confirmation (see [FUNDING_MODEL.md](FUNDING_MODEL.md)) |
| `live_deposit_collection` | As above, plus the live gateway account and webhook verified on staging |
| `self_registration` | You want new organisations to sign up without an invitation |
| `managed_service_requests` | Operations can take on new managed customers |

Turning off a live publishing flag stops new publications; campaigns already running on the provider keep running until paused there or from the campaign page.

## Plans and pricing

`/admin/plans`. Prices are hypotheses: edit amounts, limits and features as the business decides. Existing subscriptions keep their plan until the next billing period. Discounts are set per subscription with a reason.

## Emergencies

| Situation | Do |
|---|---|
| Campaign spending against the customer's wishes | Pause from the campaign page (sends pause to the provider); confirm in the provider UI |
| Suspected account compromise | Suspend the user (ends all sessions); for organisation-wide issues suspend the organisation |
| Provider API outage | Jobs retry with backoff automatically; tell affected customers; nothing to force |
| Webhook signature failures spike | Check `PAYMENT_WEBHOOK_SECRET` matches the gateway dashboard; never disable verification |
| Data incident | Follow [SECURITY.md](SECURITY.md) incident response |
